# Development specification

Technical snapshot: 2 November 2026; workspace specification v1.2 with the authorised account, calibration, qualified combined-control and separate beta-recording refinements. Implemented code, verified evidence and planned features are distinct below.

## Goal and scope

Synchronise adults' English text with one explicitly selected Lovense toy at a time. The 2 November scope expands profiles to Lush, Flexer, Nora, Domi, Velvo, Spinel, Dolce, Hush and Osci 3, with hardware-free rehearsal and an optional configured live path. Validate each physical model/configuration separately; implementation does not establish physical qualification, useful synchronisation or voluntary return.

Required beta: individual invitations, approved light/dark frontend, typed/pasted/uploaded stories and deliberate supported-site import, paragraph scoring with corrections, mobile reader, position tracking, explicit device selection, Start/Pause/Stop, intensity ceiling, opt-in local progress/folders, guided practice, private feedback and deletion controls. EPUB is optional after core checks. Generation, billing, public publishing, native apps and other brands are deferred.

Implemented locally: the Satin Editorial/Midnight Ink saved-story workspace with Light/Dark/System, direct continuous reading, background local scoring, optional corrections, collapsible library/settings, reading widths and focus mode. Explicit local saving retains opted-in stories, corrections and progress; restores are paused. One-step section level controls, a direct maximum slider and confirmed Start sit above the existing bounded simulator. The 2 November user request replaces the reader's separate ceiling-raise popup; the async lab and local hardware-check contract remain separate. Invitation sessions, server-side vendor-token issuance and the separate device-check flow remain. The nine-profile simulator and guided live connection route use separate synchronous/async device paths. The hosted live route requires private runtime credentials, authenticated per-user token issuance and a discovered eligible device. Suggestion usefulness, live SDK compatibility and hardware qualification remain unproven until observed. Physical requests remain targeted and finite at two seconds. Initial checks/default permission are at most 5/20; an explicit, checked, session-only personal-range grant can permit up to 20/20 without raising the chosen maximum or starting output. Hosted private feedback, feedback export/deletion and help are implemented; these do not erase a Cloudflare identity or browser stories. A separate Cloudflare Worker hosts the private reader and its optional Lovense token route; signed-in Access and live control checks were recorded for release `376d3049c028` on 1 November. Each later release still needs its own deployment/acceptance evidence. Its Access team/audience and enable flag are configured at runtime in the Cloudflare dashboard and preserved across repository deployments; the Python backend remains local.

The 29 October workspace revision replaces compulsory Add → Review → Read and brings opt-in story persistence into the current frontend milestone. The software-first approach continues with simulation. Hardware availability is not a prerequisite for frontend, application or algorithm work. The [roadmap](beta-roadmap.md) separates software gates S1/S2 from later hardware and release gates H1/H2. F1/F2 do not constitute a complete software beta.

## Account and controlled beta refinement on 2 November

The new requested scope is implemented in source and supersedes older account-backlog and blanket physical-5/20 statements. See [the 3 November session runbook](beta-session-2026-11-03.md) for operational checks. Current-release CI/deployment evidence must be added after execution; no physical qualification is inferred.

Cloudflare Access email OTP remains the authentication gate on the exact app and beta origins. Explicit 18+ registration creates a durable per-identity account. Account-wide and story-specific presets store a versioned toy/action map, minimum/background/preferred/maximum/recovery, rhythm, gain, active channels and master ceiling. There are at most 50 presets per account, exact bounded JSON fields and expected-revision writes. Applying any preset stops/pauses first, filters unavailable actions and clamps to current permission. Presets never contain credentials, playback arming or personal-range permission. Story-specific references are opaque local UUIDs; text/title are not uploaded and newly imported copies on another browser are not automatically matched.

The guide shows one calibration screen with a card for each available movement. Movements start selected on compatible combined connections. Each selected physical movement still has a gentle two-second test and a separate confirmation that it stopped. Qualified combinations require separate checks of all active actions and still target one toy ID. The Standard Socket Function route can expose Osci 3 oscillation and combined actions; a Basic SDK fallback stays within its narrower documented functions. Heating, guessed vibrate1/vibrate2 and full Lovense Remote parity are not implemented.

The personal range begins at 5/20. A reader may explicitly enable up to 20/20 for a checked movement only after its gentle response and targeted Stop have been observed/confirmed. Granting permission neither raises a ceiling nor starts output. Hide, expiry, disconnect, logout and device changes reset it; a saved preset cannot restore it. All nonzero commands remain finite. The lower selected maximum, including zero, always wins.

The right sidebar re-exposes movement selection, individual levels, qualified combinations, Explore controls and preset save/apply. Story dynamics may include quiet passages; optional Continuous background supplies at least the selected minimum, using the chosen background level for authored quiet passages, only in actively armed valid reading. Manual-zero overrides and maximum zero remain zero. Hold keeps chosen known output, Ease off reduces to per-action recovery levels, and Follow story returns gradually, with increases limited to two levels per renewal. None of these actions starts paused playback. The controlled fixtures have authored levels and quiet-zero semantics, distinct from manual overrides. Invalid/unknown output fails closed.

Only `https://beta.satinlore.com` can admit an explicitly consented structured beta recording. The fixed schema contains steps, allowed settings/actions, requested/simulated output vectors, optional ratings, normalized navigation/pointer data and public fixture identifiers. It excludes DOM/screen video, private story text/title, typed preset names, private URLs, device IDs and pairing/credential material. Maximum session duration is 60 minutes, 20,000 events and 4 MiB; retention is 30 days under a 128 MiB global budget. Pause/stop/withdrawal remain reachable during setup; device Stop is separate. Founder-only beta admin provides timeline playback, channel graphs and review; participants see only their own history/deletion controls. Account, browser-story and recording deletion remain separate.

Wrangler v2 adds the ReaderAccount and BetaRecordings Durable Objects automatically. Beta custom-domain routing is source-owned, while whole-host Cloudflare Access policy, optional separate beta AUD and tester allowlists remain owner-side configuration. The normal app host cannot enable beta collection with a query or client flag. Marketing CRM/email infrastructure is not reused.

The integration uses the documented [Standard Socket API](https://developer.lovense.com/docs/standard-solutions/socket-api) with a narrower [Standard JS SDK](https://developer.lovense.com/docs/standard-solutions/standard-js-sdk) fallback and Lovense Remote as the phone/Bluetooth bridge. Its per-user authentication credential is obtained through the [server token exchange](https://developer.lovense.com/docs/standard-solutions/socket-api). Check current provider contracts and applicable access before live use.

## Implemented authentication contract

- Invitation redemption accepts one token, rejects extra fields and consumes it once within a transaction. Default invitation lifetime is 24 hours; the CLI permits 1–168 hours.
- A successful redemption creates a random temporary beta UID and a session. Session lifetime defaults to one hour. This local invitation is separate from hosted verified-email account registration and does not create a durable hosted account.
- Session cookies are HttpOnly, SameSite Strict and scoped to `/api`; `Secure` follows the configured HTTPS origin. HTTP is permitted only for local development.
- Authenticated writes require the exact configured Origin and the session's CSRF token. Limits cover invitation attempts and vendor-token issuance. Bodies and vendor responses are bounded.
- Vendor issuance accepts no client UID. It checks authentication again after the external request, so expiry or logout during that request cannot return a usable application response.
- Logout revokes the application session. Existing vendor credentials have no implemented remote revocation guarantee; frontend teardown and finite commands remain necessary.

The SDK is isolated in an opaque-origin iframe without `allow-same-origin`. The hosted build embeds the bridge bundle in protected HTML under a hash-authorised content policy, so the frame does not need unauthenticated module/CORS access. Vendor network permissions are confined to this frame; the top-level reader has no vendor scripts. API responses do not enable CORS. Browser tests and live network inspection must verify these boundaries rather than inferring privacy from architecture alone.

Hosted `POST /api/lovense/session` is distinct from the local invitation implementation: it accepts exact JSON `{}`, derives a pseudonymous UID from the verified Access subject using `LOVENSE_UID_SECRET`, and exchanges the server-only `LOVENSE_DEVELOPER_TOKEN`. `LOVENSE_PLATFORM` must match the developer dashboard Website Name. Credentials expire at the earlier of the Access expiry and fifteen minutes after issuance; identity/session is revalidated after the vendor request. Persistent issuance limits are three per minute and twenty per hour in a separate Durable Object namespace. No client UID or developer token is accepted/returned in this route. The per-user `authToken` is held only in memory and sent only to its isolated bridge.

The default founder restriction remains. Optional `BETA_TESTER_EMAILS` allows at most twenty explicit email addresses only when the owner configures them; Cloudflare Access must independently allow the same tester. Changing source does not enrol a tester or provision vendor credentials. See [the beta setup guide](lovense-beta-test.md) and [Cloudflare runbook](../deploy/cloudflare/README.md).

## Device-check contract

The separate local device-check and initial guided gentle check perform one requested test at a time, with one selected device, a maximum level of 5/20 and a two-second duration. Later reader calibration may use an explicitly granted personal range within the user’s current maximum; it remains finite and deliberately requested. The separate local invitation screen retains its own authentication journey. Selection must not happen automatically. Stop targets the selected device; never omit the toy ID. Hide, disconnect, logout, selection changes and session expiry must stop or tear down the control path without automatic resumption.

The UI timer and an SDK return value do not prove physical output stopped. Hardware timing and provider behaviour remain release gates. The optional physical reading route uses a separate bounded asynchronous controller and selected action; it does not inherit physical evidence from the simulator or transport lab.

The page uses a Web Lock to prevent another same-origin tab from starting a competing hardware check. Browsers without that capability cannot connect. Continuous story playback will need its own interruption and multi-tab tests.

## Reading-loop contract — simulation and bounded live transport

The reader accepts typed/pasted/UTF-8 text content up to 500,000 bytes and 2,000 paragraphs. The blank page is a directly typable editor with a title field and an explicit action to open the draft for reading; upload and link import remain distinct right-sidebar actions. A new story opens directly into reading; it does not replace another library story or require review. Invalid input leaves existing stories intact. Stable local identities separate each story and its paragraphs. Background analysis is cancellable and cannot apply to a different story generation. Text stays session-only until explicit local-save consent. Story switching/deletion and interrupted imports invalidate stale work and leave playback paused.

The experimental English scorer requires a contact cue and a separate context cue, counting distinct concepts rather than repeated words. Broad negation/metalinguistic cues force zero. Five ordinal bands map to suggested levels **0, 1, 2, 3 and 5 out of 20**. This is a small keyword heuristic, not semantic understanding, language detection, consent classification or proof of synchronisation quality. False positives and false negatives need evaluation.

Each paragraph stores its prediction separately from a nullable manual override. Overrides accept integer levels 0–20; **zero is a real override**. Use suggestion clears only that override. Reanalysis preserves deliberate corrections. Pending/failed/invalid analysis leaves the affected automatic mapping at zero; Start requires a valid story mapping. Optional review initially exposes only current/already-read sections, with a deliberate action to reveal upcoming sections.

The reader's **−** and **+** controls move the current section's target by one whole level within its active limits. The temporary adjustment applies after the scene rhythm and movement gain. It clears on a section change and is separate from the saved correction. Manual zero, quiet boundaries, zero gain and the maximum remain authoritative. An adjustment while paused never arms playback.

Scene analysis groups neighboring matches and can carry the preceding intensity, rhythm and movement across a brief connective passage. With automatic movement switching enabled, the reader uses the matching enabled movements. If none match, it uses the chosen default unless the scene marks that movement as stopped. A stopped movement stays at zero while following the story, including during continuous background and when only one movement is selected. Authored practice fixtures retain their own levels.

In the simulator, Follow scene rhythm shapes the calibrated level over time. Builds rise, peaks play a short pair of accents, and recovery tapers. These patterns use the existing playback clock in two-second steps and then hold the final step. A scroll seek within the same paragraph preserves its place in the pattern. Each movement's enabled state, minimum and maximum, the session maximum, manual zero and Stop still apply. Other rhythm settings and the physical bridge keep their existing playback behavior.

Loom is the default local model. For the private beta, Nocturne can refine an eligible Loom sustain or peak after an explicit action for the current story. The browser sends up to 16 typed cue records to the exact-origin Worker, which validates them and calls GPT-6 Luna. Cues contain only section ordinals and limited scene categories, without story words, titles, saved identifiers or settings. Sensitive or uncertain sections stay local. Valid labels can select only local simulator patterns for the existing stage. Local intensity, movement selection, overrides and safety limits remain authoritative. A refusal, timeout or malformed result leaves the Loom mapping. Switching models pauses playback. Applied labels stay in memory and are discarded on local reanalysis or reload. The private-beta access rules and hard request quotas precede all provider calls. [Setup and checks](../deploy/cloudflare/README.md#enable-nocturne-for-the-private-beta)

The reader uses continuous document scrolling, a 180 ms settling delay and 24 px boundary hysteresis. Reading-position measurement accounts for the visible reading area and the bottom dock. Large gaps without a nearby candidate produce no position selection. Follow-scroll can be disabled; Previous/Next remains the manual fallback. Font, appearance or window-size changes preserve the selected paragraph and pause playback before repositioning. No programmatic reflow resumes it.

The controller states are `DISCONNECTED`, `READY_PAUSED`, `PLAYING` and `ERROR_PAUSED`. Start requires a connected, explicitly selected device, a current valid story mapping, a visible authorised page and explicit confirmation showing the selected mode/toy/action, strength and ceiling. Review is not a gate. Nonzero commands have a two-second duration and are dispatched no faster than once per second. Intermediate desired levels are coalesced; they are not replayed later. A reduction below current output immediately sends Stop, then a later normal tick may apply the latest bounded level. A fresh simulator starts at 10/20 and its ceiling control permits 0–20. The physical reader and gentle setup checks start within 5/20. Lowering it applies immediately, including zero. The user's direct slider input updates the ordinary reader simulator's maximum without an interrupting popup or automatic restart; increases remain bounded and use normal dispatch cadence. Programmatic/stale work must not raise the maximum. Strength + never changes the ceiling. Every Start/resume uses an explicit confirmation, and Stop cancels pending confirmation or ownership acquisition.

Stop, hide, disconnect, story switching/deletion and errors cancel scheduled dispatch. Two minutes without reading activity pauses output; a delayed playback timer also pauses instead of reviving an expired command. Returning, reconnecting, editing a level or restoring visibility never starts playback automatically. A Web Lock permits one playing simulator window per exact origin in the same browser profile. Browsers without that capability can still read/edit but cannot start playback. The reader's lock is separate from the hardware-check lock.

The reader device facade separates the synchronous simulator from asynchronous bridge transport. Physical commands remain selected-ID-only and finite. Gentle checks/default permission stay at 5/20; a separately confirmed session-only per-action personal-range grant permits at most 20/20 while respecting the current lower maximum. In-flight requests, cancellation, Stop, stale completions and reconnection must preserve the async controller contract; an SDK result is transport acceptance, not physical measurement. A lost/unconfirmed result must not be displayed as known stopped output. No reconnect, mode/action change or tab return resumes playback. Per-model physical acceptance and useful reading synchronisation remain unqualified. Local story persistence includes deletion controls; server account/preset deletion is a separate implemented action and does not erase Access identity, local stories or separately consented recordings.

## Workspace, appearance and storage contract

The workspace has a collapsible folder/story library on the left, a continuous document reader and optional Reading controls on the right, closed initially. Global Settings opens from a separate gear and contains appearance, account status, backup/restore, about, help and support. The current-reader sidebar contains import/upload, model choice, Reader/Story controls and optional corrections. Wide is the default maximum reading width, with Comfortable and Full alternatives; all shrink to the available phone viewport. Focus closes both panels while keeping the transport visible and restores the prior arrangement on exit. Below desktop width, panels become drawers/sheets rather than forcing a narrow three-column layout. Opening settings/review or reflow pauses output and preserves the selected section; manual Previous/Next remains available.

Start/Pause/Stop, section level, the chosen maximum, simulator status and capped output remain reachable outside optional settings. Confirmation dialogs expose Stop. Theme, width, font, panel and focus changes cannot start playback or alter the stored correction. See [frontend-design.md](frontend-design.md) for the shared palette and acceptance matrix.

Appearance defaults to System. The blocking same-origin script resolves the theme before styles paint and sets native `color-scheme`. Explicit Light/Dark overrides OS changes; System follows them. Only the allowlisted appearance string is stored in `satinlore.appearance`, separate from stories. Storage failure leaves appearance and reading usable.

New stories are **Session only**. **Save on this browser** explicitly opts the selected story into local persistence, including text, title, paragraph corrections, analysis version and position. Saving does not retain strength, ceiling, connection, pending confirmations or playback arming. Reload/reopen is always paused; local data is not encrypted account storage, cloud sync or backup and is visible to other users of the same browser profile. Browser clearing can remove it.

Save/rename/progress updates report actual outcomes. Storage unavailable, full, malformed or stale data must never fabricate success or make the in-memory story unreadable. Delete story removes its persisted text/corrections/progress; Delete all removes retained stories while appearance remains separate. Session-only data must not be silently saved by renaming, navigating or closing a tab. No local draft, uploaded text or saved story is sent to backend, vendor, analytics, URLs or routine logs. Deliberate AO3 link import is the narrow exception described below: the authenticated service fetches/extracts a requested public source transiently and returns text without retaining it. The test guide records exact user-facing controls and failure checks.

The current store uses local-storage key `satinlore.library.v1`, schema version 1, and serialises writes/deletes with the `satinlore-local-library` Web Lock. It permits at most 20 saved stories and 2,000,000 UTF-8 bytes for the complete JSON envelope, in addition to the per-story import limits; the workspace also limits open stories to 20 and titles to 120 characters. The record allowlist includes `id`, `title`, `text`, nullable/integer `corrections`, `position`, `analysisVersion`, `updatedAt`, `revision` and optional folder membership. The envelope may contain a bounded folder catalogue. Legacy stories remain readable; unknown fields never become playback state. Predictions are recomputed locally after restoration rather than trusted from storage. Extra fields, including strength, ceiling, credentials and playback state, are ignored on reading and never retained in a new write.

Folders share the same envelope and Web Lock as stories. At most 30 folders with names of up to 60 characters are allowed; trimmed/normalised duplicate names are rejected. Create/rename/delete explicitly persists the catalogue. An unsaved story's assignment stays in memory until Save on this browser; a saved story's assignment follows normal revision-checked saving. Deleting a folder moves its saved stories to Unfiled atomically rather than deleting them. Delete all clears both stories and the catalogue. Portable backups deliberately omit local folder IDs and restore stories to Unfiled.

Expected revisions prevent stale autosaves from recreating deleted or overwriting changed stories. A library change in another tab pauses playback and requests reload; an outdated tab cannot silently overwrite a newer saved revision. Corrupt entries remain stored for explicit recovery; valid entries can remain readable, but writes and individual deletion are blocked until the user chooses Delete all to clear the corrupt store. Delete all can remove even an unreadable envelope. Do not silently discard unreadable data. Browser quota can be lower than the application cap, and private-browser settings can deny access. Saving/deleting and simulator ownership require Web Locks; without them, session-only reading remains available and persistence reports the unsupported operation.

The hosted reader uses Cloudflare Access plus durable account/preset storage, while the separate local device-check page uses temporary invitation sessions. Story text remains local. The hosted Worker serves private feedback, data operations and optional Nocturne cue classification. The founder lab implements deterministic asynchronous scenarios. Screenshots and responsive emulation establish layout evidence only for the tested browser/build.

## Deliberate source import contract

The hosted `POST /api/story-import` route accepts a deliberately submitted public AO3 work/chapter URL. It requires the same verified Access identity and exact-origin JSON request boundary as the private app. The service validates HTTPS, canonical allowed hosts/paths, at most two redirects and a 10-second server deadline. The JSON request is capped at 4,096 bytes and its URL at 2,048 characters; upstream HTML is capped at 2,000,000 bytes and extracted text at 500,000 bytes / 2,000 paragraphs. The client also cancels after 15 seconds, and session expiry is checked again before returning story text. It forwards no browser cookies, login credentials or reader text, stores no story, executes no source scripts and reports restricted/blocked/unsupported pages as errors. Work URLs request the full work; chapter URLs import that chapter. It must not click an adult-content confirmation, bypass login or evade a site's bot controls.

AO3's downloaded UTF-8 HTML (up to 2,000,000 source bytes) can also be opened locally without executing scripts or loading page resources, subject to the same extracted-text limits; text upload and direct paste remain available. Literotica and other sites have a source-page/copy/upload fallback, not a claim of automatic scraping. Users should import only material they are entitled to use. [OTW explains AO3's built-in download formats](https://www.transformativeworks.org/why-ao3-doesnt-have-an-official-app/); [Literotica's current content-use terms](https://www.literotica.com/resources/tos) are why the current implementation provides a manual fallback there. The supported-site UI and API must tell the same story. Successful neutral parser fixtures do not establish current live-site availability.

## Setup, simulator view and future models

The guided setup journey chooses one of nine model profiles and either hardware-free simulation or a configured Lovense Remote connection. It requires an explicit discovered-device/action selection, a short low-level test and the user checking the response/stopped output before a neutral practice story. The reader can try Start/Stop, strength, maximum and scroll following before opening personal material. It can be skipped or repeated. Calibration drafts remain in memory until the reader explicitly saves an account preset; no completion, arming or personal-range permission is restored from a preset. Every Start still uses the ordinary confirmation; changing a setup step, closing/cancelling it or switching story leaves playback paused. A visible simulator graphic and bounded recent trace follow actual output snapshots, not predictions or target values. Reduced motion removes vibration movement while retaining a readable level/state.

Loom provides the default local analysis. Nocturne adds optional cue classification for admitted readers during the private beta. Paid entitlements, multi-toy control and account-linked story text storage remain future work. Qualified combined actions on one selected toy are independent of the story model, with per-action levels and checks. Hosted email sign-in, explicit account registration and account/story presets support the private reader. Browser story saving remains local.

## Remaining release criteria

- Useful automatic synchronisation with an authoritative ceiling and predictable corrections.
- Measured physical stop/expiry, no wrong-device commands and no cross-user control.
- No story text in logs, URLs, analytics, feedback defaults or vendor code; no automatic upload of local drafts/saved stories. The deliberate supported-source import service remains bounded and transient.
- Feedback remains reachable after a failed session; duplicate submissions do not duplicate rewards.
- HTTPS deployment, production cookie/proxy settings, access limits, backup/restore and rollback.
